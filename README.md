# 红色文化学习打卡系统

本项目为计算机专业项目开发实践课程项目，依据《计算机专业项目开发实践需求描述》进行分析与实现，选择的版本为 **可视化（联网）C/S**。通过桌面客户端完成红色文化景点学习、心得打卡和学习记录管理，由服务端统一处理业务并保存数据。

姓名缩写：`lfp`。项目仓库：[musicoffee/dlou-final-project](https://github.com/musicoffee/dlou-final-project)。

## 一、项目目标与技术方案

项目以课程要求为范围，优先保证功能正确、结构清楚、代码容易理解，能够在 macOS 上使用 PyCharm 或 VS Code 运行，并进行客户端与服务端联网演示。

| 部分 | 采用技术 | 主要职责 |
| --- | --- | --- |
| 桌面客户端 | Python、Tkinter | 显示窗口、接收输入、展示查询结果 |
| 网络通信 | HTTP、JSON | 客户端发送请求，服务端返回处理结果 |
| 服务端 | Python 标准库 HTTP 服务 | 验证身份和权限，处理查询、打卡及管理操作 |
| 数据库 | SQLite | 保存用户、公告、景点和学习记录 |
| 测试 | Python 自动化测试、Postman、JMeter | 验证业务功能、接口和小规模并发 |
| 版本控制 | Git、GitHub | 保存实际开发、文档和测试过程 |

系统结构：

```text
桌面客户端（Tkinter）
          │ HTTP 请求 / JSON 响应
          ▼
Python 服务端（身份校验、业务处理）
          │ SQL
          ▼
SQLite 数据库
```

客户端不直接访问数据库。虽然使用 HTTP 通信，但用户通过桌面窗口操作，因此本项目属于 C/S，而非网页 B/S。

## 二、需求分析

### 2.1 用户角色

系统包括普通用户和唯一管理员。普通用户主要完成学习、查询与打卡；管理员负责公告和景点维护、用户查询。管理员账号单独初始化，普通注册不能获得管理权限。

### 2.2 普通用户功能

| 功能 | 需求说明 |
| --- | --- |
| 注册 | 输入用户名、密码和确认密码；两次密码一致；用户名不能重复；新用户积分为0 |
| 登录与退出 | 验证用户名和密码；登录后显示用户名和学习积分；支持退出登录 |
| 公告查询 | 查询全部公告，或按标题、公告编号查询；显示标题、内容、发布日期和备注 |
| 景点查询 | 查询全部景点，或按景点名称、编号查询；显示名称、位置、红色历史介绍和热门状态 |
| 热门排行榜 | 查询打卡次数达到10次的景点，按打卡次数降序显示景点信息 |
| 学习打卡 | 选择景点、填写心得；服务端自动记录提交时间；每次打卡增加1积分 |
| 学习记录查询 | 查询本人的全部记录，或按景点编号、记录编号筛选；显示景点信息、时间和心得 |
| 记录排序 | 支持最新在前、最早在前、按景点编号排序 |
| 修改记录 | 只能修改本人打卡记录中的心得，不能修改景点或打卡时间 |
| 删除记录 | 删除本人的一次打卡记录，学习积分减1 |
| 个人信息 | 查看用户名和积分；验证原密码后修改用户名与密码 |

### 2.3 管理员功能

| 功能 | 需求说明 |
| --- | --- |
| 用户查询 | 查看用户编号、用户名、身份和积分 |
| 公告管理 | 发布、修改、删除公告；按标题和编号查询 |
| 景点管理 | 添加、修改、删除景点；维护名称、地理位置和红色历史；按名称和编号查询 |
| 热门查询 | 查看热门景点及排行榜 |

### 2.4 主要业务流程

1. 用户注册账号，确认密码一致后创建普通用户，初始积分为0。
2. 用户登录，客户端保存服务端返回的登录凭证，后续请求携带该凭证。
3. 用户查询景点，选择学习对象，阅读介绍并填写心得。
4. 服务端验证用户和景点，保存打卡记录及提交时间。
5. 客户端重新查询积分和景点打卡次数，展示最新结果。
6. 用户可查询、修改心得或删除本人的记录；删除后积分和热门次数随之变化。
7. 管理员登录后维护公告和景点，服务端检查每个管理操作的权限。

### 2.5 数据需求

| 数据表 | 主要内容 | 关联关系 |
| --- | --- | --- |
| users | 用户编号、用户名、密码哈希、盐值、身份 | 一个用户对应多条学习记录 |
| notices | 公告编号、标题、内容、发布日期、备注 | 供登录用户查询 |
| places | 景点编号、名称、位置、红色历史 | 一个景点对应多条学习记录 |
| records | 记录编号、用户编号、景点编号、时间、心得 | 通过外键关联用户和景点 |

学习积分按用户现存记录数量计算；景点打卡次数按该景点现存记录数量计算，避免重复维护计数产生不一致。

### 2.6 规则解释与实现边界

- 原需求中的“显示密码”调整为显示掩码，数据库保存加盐密码哈希，不保存可直接读取的原密码；报告中说明这一处理。
- 热门景点的条件为打卡次数大于等于10；次数相同按景点编号排序。
- 原文没有限制同一天或同一景点重复打卡，本版允许重复打卡。
- 修改心得不影响积分；删除记录会减少积分和景点次数，可能使景点退出热门榜。
- 已有打卡记录的景点不直接删除，避免破坏学习记录关联；管理员仍可修改介绍。
- 景点图片属于原需求中的“下一版本”，本版暂不实现。后续可将图片保存为文件，在数据库中存储路径。
- 普通用户只能管理本人的学习记录，管理权限在服务端检查。
- 当前范围为本机及可信局域网演示，公网部署和HTTPS配置不属于本版完成范围。

## 四、Git 提交规范

根据课程需求和提交命名截图，提交信息统一采用：

```text
type_lfp: subject
```

其中 `lfp` 为本人确认的姓名缩写。使用英文冒号，冒号后保留一个空格；不要把示意格式中的尖括号写进提交信息。

| type | 用途 | 示例 |
| --- | --- | --- |
| docs | README、学习笔记、报告、PPT等文档 | `docs_lfp: 补充需求分析与四天任务安排` |
| feat | 新增业务功能 | `feat_lfp: 实现学习打卡功能` |
| fix | 修复实际问题 | `fix_lfp: 修复打卡后的积分刷新问题` |
| test | 添加或调整测试 | `test_lfp: 补充热门景点边界测试` |

截图明确了命名结构，上表是本项目使用的类型约定；如果老师的“Git相关内容文档”对类型另有规定，收到后再核对。

### 每天上午和下午的操作

1. 保存本时段实际完成的代码、学习笔记或文档。
2. 使用 `git status` 和差异查看确认本次变更。
3. 用 `git add` 暂存本次需要提交的具体文件。
4. 用符合 `type_lfp: subject` 格式的说明进行提交。
5. 推送到 GitHub，并确认远程提交记录。
6. 保留真实的状态、暂存、提交、推送及日志操作截图，整理到Git版本控制材料中。

本次仅提交README的命令如下；后续提交应替换文件和说明：

```bash
git status
git diff -- README.md
git add README.md
git commit -m "docs_lfp: 补充需求分析与四天任务安排"
git push -u origin main
git log -5 --date=local --pretty=format:"%h %ad %s"
```

首次提交前README是未跟踪文件，普通 `git diff` 不显示其内容；暂存后可用 `git diff --cached -- README.md` 检查。

截图可以按 `第1天_上午_Git操作.png`、`第1天_下午_Git操作.png` 的方式整理。Mac可按 `Command + Shift + 4` 框选终端内容截图。保存截图时隐藏密码、Token等敏感信息。

每次提交以真实完成时间和内容为准，不补造历史提交。当前尚未设置定时提交任务；代码、数据库和其他本地文件不会随本次README提交一起上传。真实数据库、密码、Token和本地配置不进入仓库。
